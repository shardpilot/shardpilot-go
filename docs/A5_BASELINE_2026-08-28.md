# Allocation baseline — Go SDK, 2026-08-28

- Date: **2026-08-28**
- Commit measured: `9db83d94336d384434d2fa47cddc65af37d07cd1` (`origin/main`)
- Toolchain: `go1.27.0 darwin/arm64`
- Machine: Apple M1 Max, 10 CPUs, macOS 26.5.2 — **a laptop, not the CI runner**
- Produced by: `SHARDPILOT_BENCHTIME=3s scripts/run_benchmarks.sh`

## Why this file exists at all

Automatic session-lifecycle events are planned for this SDK. They change
allocation, batching cadence and event volume, so **once they land, "what did
this cost before" is unrecoverable.** The measurement had to be taken now or
not at all.

There was no series to append to. `/bench/` is gitignored — anchored,
deliberately, as CI working output — `git ls-files bench/` returns 0, and the CI
artifact carries `retention-days: 30`. Every number this repository has ever
produced has expired. `scripts/run_benchmarks.sh:18-21` already says what is
missing:

> "a threshold needs a baseline measured on hardware comparable to the runner …
> a regression gate is a separate decision"

This is the first dated entry of that series. It is deliberately **not** in
`/bench/`, which would ignore it.

## The load-bearing result is not any single number

**`ns/op` on this machine is not a usable baseline axis.** Run-to-run spread
between two consecutive runs of unchanged code, same binary, same benchtime, is
**6.9 % to 64.3 %**. A later comparison against a changed SDK could show a 40 %
regression that is entirely noise, and — worse — could hide a real 30 % one.

**`allocs/op` is exact.** Identical to the unit across both runs for all five
benchmarks. `B/op` drifts under 0.15 %, which is map iteration order, not cost.

So the axis a future comparison must use is **allocations and bytes**, and any
wall-time claim needs either the CI runner or a many-run distribution, neither of
which this file provides.

## A second instrument note

The runner pins `-benchtime=100x` by default (`run_benchmarks.sh:416-420`), for
CI determinism. That pin makes it useless as a baseline. Measured at `100x`
against the same commit:

| Benchmark | ns/op at 100x | ns/op at 3s (r1) | divergence |
|---|---:|---:|---:|
| `EnqueueMapPayload` | 1 257 | 3 114 | 2.5× |
| `BuildBatchMapPayloads` | 327 905 | 619 115 | 1.9× |
| `StatsCollectorAggregation` | 98.33 | 22.97 | 4.3× |
| `CompressBatchBody` | 22 046 | 29 302 | 1.3× |
| `ClientEmit` | 57 362 | 99 489 | 1.7× |

Allocation counts were identical at both settings. A hundred iterations is a
sample, not a measurement, and it diverges by up to 4× from a settled one — in
both directions, so it is not even a consistent bias.

Uniform `N = 100` across all five benchmarks is the signature of a broken
instrument, and was checked as one before being trusted: it is the deliberate pin
at line 420, not a failure.

## Axes, including the ones not varied

Varied: benchtime (`100x`, `3s`), and repetition (two runs at `3s`).

**Not varied, and each is a real limit on what this file can be compared to:**

- **One machine.** Apple M1 Max laptop. Not the CI runner, so these numbers
  cannot be compared to anything CI produces, in either direction.
- **One OS and architecture.** `darwin/arm64` only. No Linux, no amd64.
- **One toolchain.** `go1.27.0`.
- **Thermal state uncontrolled.** Two runs, back to back, on a machine doing
  other work — which is the most likely source of the `ns/op` spread above.
- **One SDK.** Go only. The four engine SDKs answer device-shaped questions
  (frame cost, battery) that this harness cannot ask, and their baseline is not
  in this file.
- **Config not varied.** Whatever `origin/main` defaults to at the commit above.

## What this does and does not establish

Establishes: the allocation and byte cost of the Go SDK's five tracked
benchmarks, on this machine, at this commit, before automatic collection.

Does **not** establish: any wall-time figure durable enough to compare against;
anything about the four engine SDKs; anything about behaviour on the CI runner;
anything about battery or frame cost, which is the question studios actually ask
and which a later device-side measurement owes.
